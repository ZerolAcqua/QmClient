# 客户端运行期开销优化

## 范围（2026-09-17）

用户追问客户端优化，要求继续最初的全客户端卡顿检测与性能优化，不能仅交付动效修改。沿用已确认授权：可以优化客户端及引擎热点，保留协议、玩法、物理、预测、画面效果和更新时机；先补测试代码再实现，只运行 quick 源码门禁，不编译、不执行测试、不启动客户端。

本轮处理由当前源码直接证明的重复扫描、计算、分配和诊断准备开销。历史 3.6.1 日志不作为当前工作树的性能基线；本轮不以静态复杂度推导实际 FPS 或卡顿根因。

## 调查及实施范围

| 路径 | 原开销 | 保持的边界 |
| --- | --- | --- |
| 服务器浏览器 | HTTP 完成/缓存刷新已排序，遗留待排序标记导致下一次 Update 再次完整排序；同一次筛选为每个服务器重新解析相同搜索串；社区查找按值复制包含玩家信息的整个服务器对象 | 筛选语义、QuickSearchHit、好友/收藏处理、排序结果及新增排序请求不丢失 |
| 钩子提示线 | 每个玩家每次绘制新建线段与加粗四边形 vector，反复分配释放 | 钩子提示模拟、目标筛选、传送选择、顶点、颜色和绘制顺序 |
| Tee 拖尾 | 每个细分点重复计算同一原始段的长度、方向、切线 | 原公式、插值顺序、细分预算、透明混合、画质与时间 |
| 皮肤失败通知 | 没有新失败状态时仍遍历完整皮肤表 | 通知收集时机、原遍历顺序、恢复/再次失败及通知回调中新失败 |
| 皮肤优先请求 | 无背景条目时仍统计完整皮肤表；达到回收门槛后仍继续精确计数 | 请求者跳过、背景回收顺序、任务取消、回收数量及预算 |
| 托管 Tee 渲染信息回收 | 每删一项重新查找并移动 vector 尾部，多个过期引用造成 O(N²) 工作 | 相同 use_count 判据、仍被引用的条目、稳定顺序及原帧末回收点 |
| 关闭性能诊断的普通帧 | 仍调用高精度时钟并格式化最终被诊断开关丢弃的文本 | 默认计时器行为、开启诊断的采集、独立 UI 调试、动画计数及菜单调度 |

本轮未采用全局皮肤状态增量计数或随意延迟资源应用：目录合并、入表前失败和直接加载的生命周期不同，错误缓存会影响当帧预算。新闻缓存写盘、WebSocket 大消息解析和小窗完整场景绘制仍需当前版本场景数据来确定下一轮优先级。

## 实现结果

- `serverbrowser.cpp`：在 `Sort()` 入口消费当前待排序请求，保留排序中新产生的请求；搜索及排除词在一次 `Filter()` 中只解析一次；社区查找按引用访问服务器信息。HTTP 导入的收藏和允许 ping 在 `Add()` 读取、由 `SetInfo()` 保留。
- `players.cpp/.h`：线段和四边形缓冲由玩家组件持有，调用开始清空内容并保留容量。两个绘制入口串行执行，图形接口提交时立即复制顶点，主视图与小窗不共享未提交内容。
- `qm_tee_trail.cpp/.h`：每个原始段准备一次长度、方向及切线，每个细分点只求值原三次公式；没有降低采样数或特效质量。
- `skins.cpp/.h`：失败状态转换触发待扫描标记；无新失败时收集函数直接返回。标记在扫描前消费，通知回调中的新失败留到下轮；刷新保留标记，关闭时随皮肤表清空。优先请求在无背景条目时跳过计数，到达门槛后停止计数。
- `gameclient.cpp`：托管 Tee 渲染信息采用稳定的一次压缩删除，最坏删除工作由 O(N²) 降为 O(N)。当前创建入口不会插入重复托管指针，刷新回调没有持有其他托管条目，不存在删除导致后续条目引用计数连锁变化的路径。
- `perf_timer.h`、`gameclient.cpp`、`QmRt.cpp`：计时器增加显式关闭模式，仅接入纯诊断计时点；默认计时和资源预算计时保持启用。UI 独立 debug 保留计时，节点及动画计数始终更新；关闭日志或未到汇总采样点时跳过对应文本准备。

上述是源码可确认的工作量减少，尚未量化 CPU 时间、帧率、帧时间分位数或实机卡顿改善。引擎主循环和渲染入口已有关闭诊断的快速路径，本轮保留；没有调整帧率限制、网络更新、输入、预测或物理时序。

审查 findings：未发现本轮新增的正确性问题。服务器初次排序保留收藏及允许 ping 已补断言；皮肤新入表、初始失败、刷新和回调路径均经 `SetState()`，没有发现漏置扫描标记的赋值入口。关闭诊断后 UI 耗时统计归零，现有功能消费者只读取节点与动画计数。
